# Chapter 11: Writing Automated Tests

--- card: read id=c01 xp=5 title="What a test is"
The type system catches a whole class of bugs, but it cannot know that `add(2, 2)` should be `4`. Tests state what the code is *supposed* to do, and the test runner checks it.

A test is a function with the `#[test]` attribute:

```rust
pub fn add(a: u64, b: u64) -> u64 { a + b }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn two_plus_two() {
        assert_eq!(add(2, 2), 4);
    }
}
```

`cargo test` builds a test binary, runs every `#[test]` function on its own thread, and reports `ok` or `FAILED` for each. A test fails when it **panics**: an `assert!` that is false, an `unwrap` on an `Err`, an explicit `panic!`, or an out-of-bounds index.

`#[cfg(test)]` means the whole `tests` module is only compiled when testing, so it costs nothing in the real binary. `use super::*;` pulls the parent module's items in, including **private** ones: Rust lets you test private functions directly.

You have been running tests since chapter 1; every exercise in this course is a `cargo test` invocation.

*Book: 11.1 "How to Write Tests"*

--- card: read id=c02 xp=5 title="The assertion macros"
- `assert!(cond)` fails if `cond` is false.
- `assert_eq!(left, right)` fails if they differ, and prints **both** values. The arguments need `PartialEq` (to compare) and `Debug` (to print), which is why structs under test derive both.
- `assert_ne!(left, right)` fails if they are equal.

Every one of them accepts a custom message after the required arguments, with `format!` syntax:

```rust
assert!(
    result.contains("Carol"),
    "Greeting did not contain name, value was `{result}`"
);
```

The message is what you will read at 2 a.m. when the test fails in CI. Spend a second on it.

--- card: predict id=c03 xp=15 title="Which test fails?"
```rust
fn double(x: i32) -> i32 { x * 2 }

#[test]
fn a() { assert_eq!(double(2), 4); }

#[test]
fn b() { assert_ne!(double(0), 0); }

#[test]
fn c() { assert!(double(-1) < 0, "negatives stay negative"); }
```
? Which tests fail?
- [ ] `a` only
- [x] `b` only
- [ ] `b` and `c`
- [ ] None of them
> `double(0)` is `0`, so `assert_ne!(0, 0)` panics with `left == right`. `a` and `c` hold. Each test runs independently; one failure does not stop the others.

--- card: read id=c04 xp=5 title="Expected panics and Result tests"
When the *correct* behaviour is to panic, say so:

```rust
#[test]
#[should_panic(expected = "between 1 and 100")]
fn guess_too_high() {
    Guess::new(200);
}
```

The test passes only if the code panics **and** the panic message contains the `expected` text. Always give `expected`; without it, a panic for the wrong reason (a typo that indexes out of bounds, say) would also pass.

Tests can also return a `Result`, so that `?` works inside them:

```rust
#[test]
fn parses() -> Result<(), String> {
    let n: i32 = "42".parse().map_err(|e| format!("{e}"))?;
    assert_eq!(n, 42);
    Ok(())
}
```

An `Err` return fails the test. You cannot combine `should_panic` with a `Result`-returning test; use `assert!(value.is_err())` for that case.

--- card: quiz id=c05 xp=15 title="should_panic" multi
```rust
fn checked_div(a: i32, b: i32) -> i32 {
    if b == 0 { panic!("division by zero"); }
    a / b
}
```
? Which tests **pass**?
- [x] `#[test] #[should_panic] fn t1() { checked_div(1, 0); }`
- [x] `#[test] #[should_panic(expected = "by zero")] fn t2() { checked_div(1, 0); }`
- [ ] `#[test] #[should_panic(expected = "overflow")] fn t3() { checked_div(1, 0); }`
- [ ] `#[test] #[should_panic] fn t4() { checked_div(4, 2); }`
- [x] `#[test] fn t5() { assert_eq!(checked_div(4, 2), 2); }`
> `expected` is a substring check against the panic message. `t3` panics with the wrong message; `t4` does not panic at all, which fails a `should_panic` test.

--- card: read id=c06 xp=5 title="Controlling the test run"
```text
cargo test                          # everything
cargo test two_plus                 # only tests whose name contains "two_plus"
cargo test -- --test-threads=1      # run serially (tests share no state by default)
cargo test -- --show-output         # show println! output from passing tests too
cargo test -- --ignored             # run only the #[ignore]d tests
cargo test -- --include-ignored     # run everything
```

Arguments before `--` go to cargo; after `--` they go to the test binary.

By default tests run **in parallel**, so two tests writing the same file will interfere. Give each test its own data, or run with one thread.

Output of a *passing* test is captured and hidden; a failing test's output is shown. `#[ignore]` marks a slow test to skip in the usual run.

*Book: 11.2 "Controlling How Tests Are Run"*

--- card: read id=c07 xp=5 title="Unit tests and integration tests"
**Unit tests** live in the same file as the code, in a `#[cfg(test)] mod tests`. They can reach private items and test one piece in isolation.

**Integration tests** live in a `tests/` directory next to `src/`. Each file there is compiled as its own crate that depends on your library, exactly like an external user would:

```rust
// tests/integration_test.rs
use adder::add_two;

#[test]
fn it_adds_two() {
    assert_eq!(add_two(2), 4);
}
```

They can only use the library's public API, which is the point: they prove the public surface works. Shared helpers go in `tests/common/mod.rs` (the `mod.rs` form, so cargo does not treat it as a test file).

Binary crates (`src/main.rs` only) cannot be integration-tested, because there is nothing to `use`. This is why the guessing game and minigrep keep their logic in `lib.rs` and leave `main.rs` thin. The exercise files in this course are integration tests too: each `[[test]]` target in a chapter's `Cargo.toml` is one.

--- card: quiz id=c08 xp=15 title="Organisation" multi
? Which statements are true?
- [x] A unit test in a `#[cfg(test)]` module can call private functions of its parent module.
- [ ] Integration tests in `tests/` can call private functions of the library.
- [x] Each file in `tests/` becomes a separate crate.
- [x] Tests run in parallel by default.
- [ ] `cargo test` prints the `println!` output of every test.
- [x] Keeping logic in `lib.rs` makes a binary testable.
> Integration tests see only `pub` items, because they are external crates. Output of passing tests is captured unless you pass `--show-output`.
