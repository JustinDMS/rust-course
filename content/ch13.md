# Chapter 13: Functional Language Features: Iterators and Closures

--- card: read id=c01 xp=5 title="Closures: functions that capture"
A **closure** is an anonymous function you can store in a variable or pass to another function. Unlike a `fn`, it can use variables from the scope it is defined in.

```rust
let threshold = 10;
let is_big = |x: i32| x > threshold;      // captures `threshold`
println!("{}", is_big(12));
```

Syntax: parameters between `|`, then the body. Types are usually inferred from the first use; a block body `{ ... }` is allowed when there is more than one expression. Once a closure's parameter types are inferred, they are fixed: calling `let f = |x| x; f(5); f("a");` is an error.

How a closure captures each variable is decided by what the body does with it, from least to most restrictive:

- **by shared reference** when it only reads (`|| println!("{list:?}")`),
- **by mutable reference** when it mutates (`|| list.push(7)`), which requires the closure binding to be `mut` and counts as a live `&mut` borrow between definition and last call,
- **by value** when it moves the variable out (`|| drop(list)`).

The `move` keyword forces capture by value even when the body only reads. That is what you want when the closure will outlive the scope, typically when it is returned from a function or sent to another thread.

--- card: read id=c03 xp=5 title="Fn, FnMut and FnOnce"
Functions that accept closures describe what they will do with them through three traits:

- **`FnOnce`**: may be called once. Every closure implements it. A closure that moves a captured value *out* of its body implements only this.
- **`FnMut`**: may be called repeatedly and may mutate its captures.
- **`Fn`**: may be called repeatedly, mutates nothing, and can be called concurrently. The most restrictive bound to satisfy, the easiest to call.

Look at the standard library to see them in use: `Option::unwrap_or_else<F: FnOnce() -> T>(self, f: F)` calls `f` at most once, so it asks for the least. `slice::sort_by_key<K, F: FnMut(&T) -> K>` calls its closure once per element, so it needs `FnMut`.

When you write a function taking a closure, choose the **weakest** trait that your body needs: `FnOnce` if you call it once, `FnMut` if you call it in a loop, `Fn` only if you must. Plain `fn` items implement all three, so a function name can be passed wherever a closure can.

A closure returned from a function usually needs `move`, because the function's locals die when it returns: `fn adder(n: i32) -> impl Fn(i32) -> i32 { move |x| x + n }`.

--- card: read id=c05 xp=5 title="Iterators are lazy"
An **iterator** produces a sequence of values, one `next()` call at a time:

```rust
pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
    // ... dozens of provided methods built on next
}
```

Anything that implements `next` gets the whole toolbox: `map`, `filter`, `sum`, `collect`, `zip`, `enumerate`, `rev`, `take`, `skip`, `any`, `all`, `position`, `max_by_key`, `count`, and more.

Three ways to iterate a collection:

- `v.iter()` yields `&T`; the collection is borrowed.
- `v.iter_mut()` yields `&mut T`.
- `v.into_iter()` yields `T` and **consumes** the collection. `for x in v` uses this one.

Iterators are **lazy**: `v.iter().map(|x| x + 1)` does nothing until something pulls values out. **Consuming adaptors** such as `sum`, `count`, `collect` and `for` loops drive the iterator to the end. **Iterator adaptors** such as `map` and `filter` return a new iterator and run nothing yet. A `map` whose result is never used is a warning: `unused Map that must be used`.

--- card: read id=c07 xp=5 title="The pipeline shape"
Most iterator code is a chain: a source, some adaptors, one consumer.

```rust
let total: u32 = shoes
    .iter()
    .filter(|shoe| shoe.size == my_size)   // keep some
    .map(|shoe| shoe.price)                // transform
    .sum();                                // consume
```

- `collect()` builds a collection from any iterator. The target type comes from the annotation: `let names: Vec<String> = ...collect();` or `collect::<Vec<_>>()`. It can also build a `String` from chars, a `HashMap` from pairs, or a `Result<Vec<T>, E>` from an iterator of `Result`s (stopping at the first `Err`).
- `filter` takes a closure that receives a **reference** to each item and returns `bool`. With `iter()` the items are already references, so the closure sees `&&T`; patterns like `|&&x|` or `|x| **x` deal with that, or `.copied()` first for `Copy` types.
- `map` transforms each item; `filter_map` does both and drops `None`s.
- `enumerate` pairs each item with its index; `zip` pairs two iterators; `windows(2)` on a slice gives overlapping pairs.

Closures in adaptors capture their environment like any other: `filter(|s| s.size == my_size)` reads `my_size` from the enclosing function.

--- card: quiz id=c08 xp=15 title="Read the chain"
```rust
let v = vec![3, 8, 1, 9, 4];
let r: Vec<i32> = v.iter().filter(|&&x| x > 2).map(|x| x * 10).collect();
```

- [x] `[30, 80, 90, 40]`
- [ ] `[30, 80, 10, 90, 40]`
- [ ] `[80, 90]`
- [ ] `[3, 8, 9, 4]`

--- card: read id=c09 xp=5 title="Loops versus iterators"
The same work, two ways:

```rust
// loop
let mut total = 0;
for value in &values {
    if value % 2 == 0 {
        total += value * value;
    }
}

// iterator
let total: i32 = values.iter().filter(|v| *v % 2 == 0).map(|v| v * v).sum();
```

The iterator version has no mutable accumulator, no index, and reads as *what* rather than *how*. It is also no slower: iterators are a **zero-cost abstraction**. The adaptors are generic and inlined, and the compiler turns the chain into the same loop you would write by hand, often unrolled. The book's benchmark shows the iterator version of `search` running marginally *faster* than the loop.

Prefer iterators when the shape fits (transform, filter, aggregate). Reach for a loop when the control flow is irregular: early exits with state, several collections updated at once, or when the iterator version needs a comment to explain.

Two improvements from chapter 13.4:

`Config::build` took a slice and cloned two strings out of it. With an iterator it can take ownership of each argument as it arrives:

```rust
pub fn build(mut args: impl Iterator<Item = String>) -> Result<Config, &'static str> {
    args.next();                       // program name
    let Some(query) = args.next() else { return Err("Didn't get a query string") };
    let Some(file_path) = args.next() else { return Err("Didn't get a file path") };
    ...
}
```

`env::args()` is exactly such an iterator, so `main` passes it straight in. And `search` becomes one expression: `contents.lines().filter(|line| line.contains(query)).collect()`.
