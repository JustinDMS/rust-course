# Chapter 10: Generic Types, Traits, and Lifetimes

--- card: read id=c01 xp=5 title="Generics: one function, many types"
Two functions that differ only in the type they handle are one function waiting to be written:

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

`<T: PartialOrd>` declares a type parameter `T` and **bounds** it: `T` must implement `PartialOrd`, which is what makes `>` available. Without the bound, the body does not compile; Rust checks a generic function once, against its bounds, not once per call site.

Structs, enums and methods take type parameters the same way:

```rust
struct Point<T> { x: T, y: T }

impl<T> Point<T> {
    fn x(&self) -> &T { &self.x }
}

impl Point<f64> {                       // only for f64 points
    fn distance_from_origin(&self) -> f64 { (self.x.powi(2) + self.y.powi(2)).sqrt() }
}
```

`Option<T>` and `Result<T, E>` are exactly this. At compile time Rust **monomorphizes**: it generates a separate copy of `largest` for each `T` actually used, so generics cost nothing at run time.

*Book: 10.1 "Generic Data Types"*

--- card: read id=c03 xp=5 title="Traits: shared behaviour"
A **trait** lists method signatures that a type can promise to provide:

```rust
pub trait Summary {
    fn summarize_author(&self) -> String;

    fn summarize(&self) -> String {                      // default method
        format!("(Read more from {}...)", self.summarize_author())
    }
}

impl Summary for Tweet {
    fn summarize_author(&self) -> String { format!("@{}", self.username) }
}
```

- An `impl Trait for Type` block must provide every method without a default, and may override the ones with one.
- Default methods may call the required ones, as `summarize` does.
- The **orphan rule**: you can implement a trait for a type only if the trait or the type is defined in your crate. So you can implement `Display` for your `Tweet`, or your `Summary` for `Vec<T>`, but not `Display` for `Vec<T>`.
- To call a trait's methods, the trait must be in scope (`use`), which is why `use std::io::Write;` or `use rand::Rng;` keeps appearing.

Many standard traits can be **derived**: `#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Default)]`. Others, such as `Display`, you write by hand.

*Book: 10.2 "Traits: Defining Shared Behavior"*

--- card: read id=c04 xp=5 title="Traits as parameters and return types"
Four ways to say "any type that implements `Summary`":

```rust
fn notify(item: &impl Summary) { ... }                  // impl Trait syntax
fn notify<T: Summary>(item: &T) { ... }                 // trait bound
fn notify<T: Summary + Display>(item: &T) { ... }       // several bounds
fn notify<T>(item: &T) where T: Summary + Display { ... }   // where clause
```

They are equivalent for one parameter. The generic form lets two parameters share a type (`fn pair<T: Summary>(a: &T, b: &T)`); `where` keeps long bound lists readable.

A function can **return** `impl Summary`, meaning "some concrete type that implements `Summary`, which I am not telling you". The restriction: the body must return **one** concrete type. An `if` that returns a `Tweet` in one branch and an `Article` in the other does not compile; that case needs trait objects (`Box<dyn Summary>`, chapter 18).

Bounds also gate methods: `impl<T: Display + PartialOrd> Pair<T> { fn cmp_display(&self) ... }` gives `cmp_display` only to `Pair`s whose `T` qualifies. The standard library's `impl<T: Display> ToString for T` is a *blanket implementation*: every `Display` type gets `.to_string()` for free.

--- card: predict id=c05 xp=15 title="Missing bound"
```rust
fn show_all<T>(items: &[T]) -> String {
    let mut out = String::new();
    for item in items {
        out.push_str(&format!("{item} "));
    }
    out
}

fn main() {
    println!("{}", show_all(&[1, 2, 3]));
}
```
? What happens?
- [ ] Prints `1 2 3 `
- [x] Compile error: `T` doesn't implement `std::fmt::Display`
- [ ] Compile error: `items` must be a `Vec<T>`
- [ ] Prints `[1, 2, 3]`
> The body uses `{item}`, which needs `Display`, but nothing promised that `T` has it. The call site would be fine (`i32` is `Display`); generic functions are checked against their bounds, not their callers. Add `T: std::fmt::Display`.

--- card: read id=c07 xp=5 title="Lifetimes: how long a reference is valid"
Every reference has a **lifetime**: the region of code during which it is valid. Usually the compiler infers them. Sometimes it cannot, and you annotate.

```rust
fn longest(x: &str, y: &str) -> &str {      // error[E0106]: missing lifetime specifier
```

The compiler does not know whether the returned reference borrows from `x` or from `y`, so it cannot check callers. You tell it:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Read `'a` as "some lifetime": the returned reference is valid for as long as **both** inputs are. Annotations never change how long anything lives; they describe relationships so the borrow checker can reject misuse:

```rust
let string1 = String::from("long string is long");
let result;
{
    let string2 = String::from("xyz");
    result = longest(string1.as_str(), string2.as_str());
}
println!("{result}");       // error: `string2` does not live long enough
```

`result` could point into `string2`, which is gone. Rejected. Had `longest` only ever returned `x`, you would write `fn longest<'a>(x: &'a str, y: &str) -> &'a str` and the same code would compile.

*Book: 10.3 "Validating References with Lifetimes"*

--- card: predict id=c08 xp=20 title="Which one lives long enough?"
```rust
fn first<'a>(x: &'a str, _y: &str) -> &'a str { x }

fn main() {
    let a = String::from("alpha");
    let r;
    {
        let b = String::from("beta");
        r = first(&a, &b);
    }
    println!("{r}");
}
```
? What happens?
- [x] Prints `alpha`
- [ ] Compile error: `b` does not live long enough
- [ ] Compile error: `r` is possibly uninitialised
- [ ] Prints `beta`
> The signature says the result borrows only from `x`. `b` dying at the inner `}` is irrelevant, because `r` cannot be pointing into it. With `_y: &'a str` instead, the same program would be rejected.

--- card: read id=c09 xp=5 title="Elision, structs and 'static"
You have written many functions with references and no `'a`. That is **lifetime elision**: three rules the compiler applies before complaining.

1. Each reference parameter gets its own lifetime.
2. If there is exactly one input lifetime, it is assigned to all output references.
3. If one of the parameters is `&self` or `&mut self`, its lifetime goes to all outputs.

`fn first_word(s: &str) -> &str` hits rule 2. `fn longest(x: &str, y: &str) -> &str` has two input lifetimes and no `self`, so none of the rules apply and you must annotate.

**Structs holding references** need a lifetime parameter, because the struct cannot outlive what it points at:

```rust
struct Excerpt<'a> { part: &'a str }

impl<'a> Excerpt<'a> {
    fn part(&self) -> &str { self.part }     // rule 3
}
```

**`'static`** means "valid for the whole program". String literals are `&'static str`: they live in the binary. The compiler sometimes suggests `'static` to make an error go away; that is almost always wrong, and the real fix is in how long the data lives.

> One input reference, or a `&self`, lets elision fill in the output. Two inputs with a reference output need `'a`. A struct with a reference field always needs one. A return with no inputs must be `'static` (there is nothing else it could borrow from), and that is written explicitly.
