# Chapter 4: Understanding Ownership

--- card: read id=c01 xp=5 title="Why ownership exists"
Every language has to answer one question: **when is a piece of memory no longer needed?**

- Garbage-collected languages (Java, Go, C#) answer it at run time, with a collector that costs CPU and pauses.
- C and C++ leave the answer to you, and get it wrong often enough that a whole industry exists to find the resulting bugs.
- Rust answers it **at compile time**, with a set of rules the compiler checks. Break a rule and the program does not compile. Follow them and memory is freed at exactly the right moment, with no collector and no leaks.

Those rules are *ownership*. They are the reason Rust feels different from everything you have used before, and the reason the borrow checker argues with you. This chapter is the one to slow down on.

--- card: read id=c02 xp=5 title="Stack and heap, in one minute"
Both are memory your program can use at run time. They differ in how they are organised.

**The stack** is last-in, first-out. Pushing and popping are a single instruction. Everything on it must have a **known, fixed size** at compile time: integers, floats, booleans, `char`s, fixed-size arrays, and *pointers* into the heap.

**The heap** is for data whose size is unknown at compile time or can change: the text of a `String`, the elements of a `Vec`. Asking for heap space (*allocating*) means finding a free block, bookkeeping, and getting back a pointer. Slower, and the data is further away from the CPU's caches.

Ownership is mostly about the heap: who is responsible for giving an allocation back, and when.

--- card: read id=c03 xp=5 title="The three rules"
1. Each value in Rust has exactly one **owner**.
2. There can only be one owner at a time.
3. When the owner goes out of scope, the value is **dropped** (its memory is freed).

A *scope* is the region of code where a variable is valid: from its `let` to the closing `}` of the block it lives in.

```rust
{                                   // s is not valid here; not declared yet
    let s = String::from("hello");  // s is valid from this point
    // ... use s ...
}                                   // scope ends: s is dropped, memory freed
```

The call that frees the memory is a function named `drop`. Rust inserts it for you at the closing brace. C++ programmers know this pattern as RAII; Rust makes it the only option.

--- card: code id=c04 xp=5 title="String lives on the heap"
```rust
fn main() {
    let mut s = String::from("hello"); // allocates 5 bytes on the heap
    s.push_str(", world");             // may reallocate to make room
    println!("{s}");
    println!("length {} bytes, capacity {} bytes", s.len(), s.capacity());
}                                      // s dropped here
```
A string literal like `"hello"` is baked into the executable and cannot grow. `String` is a growable buffer on the heap. On the stack, `s` is just three words: a pointer to the buffer, its length, and its capacity. Run it and look at the capacity.

--- card: read id=c05 xp=5 title="Assignment moves"
Here is where Rust parts ways with other languages.

```rust
let s1 = String::from("hello");
let s2 = s1;
```

In most languages that line makes `s2` a second handle to the same text. If Rust did that, both `s1` and `s2` would drop the buffer when they go out of scope: a **double free**. Copying the heap data instead would be safe, but expensive and surprising.

Rust does neither. The assignment **moves** the value: `s2` becomes the owner, and **`s1` is no longer valid**. Using `s1` afterwards is a compile error, not a run-time one. Only the three stack words are copied; the heap buffer is untouched.

> error[E0382]: borrow of moved value: `s1`

If you really want a deep copy, say so: `let s2 = s1.clone();`. Seeing `.clone()` in code is a signal that something potentially expensive happens there.

--- card: read id=c09 xp=5 title="Functions move too"
Passing a value to a function works exactly like assigning it to a variable.

```rust
fn takes(s: String) { println!("{s}"); }   // s dropped at the end of takes
fn copies(n: i32)   { println!("{n}"); }

let s = String::from("hi");
takes(s);        // s MOVED into the function; invalid from here
let n = 5;
copies(n);       // n COPIED; still usable
```

Returning a value moves it back out to the caller. You *could* write every function to take ownership and return it again:

```rust
fn measure(s: String) -> (String, usize) {
    let len = s.len();
    (s, len)     // give it back
}
```

That is tedious. Rust has a better answer for "I just want to look at it": **references**, next.

--- card: read id=c10 xp=5 title="References: borrow, don't take"
A **reference** lets you refer to a value without owning it. Write `&value` to create one and `&Type` in a signature to accept one.

```rust
fn measure(s: &String) -> usize {
    s.len()
}

let s = String::from("hi");
let len = measure(&s);   // lend s out
println!("{s} is {len} long");   // s still ours
```

Creating a reference is called **borrowing**. The function uses the value and gives it back, without a move and without a clone. When the reference goes out of scope nothing is dropped, because the reference never owned anything.

References are **immutable by default**: `measure` cannot change `s` through `&String`. To allow changes, both sides say so explicitly.

```rust
fn exclaim(s: &mut String) {
    s.push('!');
}

let mut s = String::from("hi");   // the owner must be mut too
exclaim(&mut s);
```

--- card: code id=c11 xp=5 title="Mutable borrow in action"
```rust
fn add_suffix(name: &mut String, suffix: &str) {
    name.push(' ');
    name.push_str(suffix);
}

fn main() {
    let mut hero = String::from("Samus");
    add_suffix(&mut hero, "Aran");
    add_suffix(&mut hero, "the Hunter");
    println!("{hero}");
}
```
Each call borrows `hero` mutably for exactly the duration of the call, then hands it back. Try removing `mut` from `let mut hero` and read the error.

--- card: read id=c12 xp=5 title="The two borrowing rules"
The compiler enforces two rules about references. Together they rule out data races and iterator invalidation at compile time.

1. At any given time you can have **either** one mutable reference **or** any number of immutable references to a value. Not both.
2. References must always be **valid**: a reference can never outlive the value it points to.

Rule 1 is checked over the region where each reference is actually *used*, not the whole block. A reference's "life" ends at its last use, so this compiles:

```rust
let mut s = String::from("hello");
let r1 = &s;
println!("{r1}");      // last use of r1
let r2 = &mut s;       // fine: no shared borrow is still alive
r2.push('!');
```

Rule 2 is what stops a function from returning a reference to one of its own local variables: the local is dropped when the function returns, so the reference would dangle. The fix is to return the owned value instead.

--- card: predict id=c13 xp=15 title="Two at once"
```rust
fn main() {
    let mut s = String::from("hello");
    let a = &mut s;
    let b = &mut s;
    a.push('!');
    b.push('?');
    println!("{s}");
}
```
? What happens?
- [ ] Prints `hello!?`
- [x] Compile error: cannot borrow `s` as mutable more than once at a time
- [ ] Prints `hello?!`
- [ ] Panics at run time
> `a` is still used after `b` is created, so two mutable borrows overlap. Rust rejects it with E0499. If the `a.push('!')` line came *before* `let b`, the program would compile, because `a` would be dead by then.

--- card: predict id=c14 xp=20 title="Mixing shared and mutable"
```rust
fn main() {
    let mut scores = vec![3, 1, 2];
    let first = &scores[0];
    println!("first = {first}");
    scores.push(4);
    println!("{scores:?}");
}
```
? What happens?
- [x] Prints `first = 3` then `[3, 1, 2, 4]`
- [ ] Compile error: cannot borrow `scores` as mutable because it is also borrowed as immutable
- [ ] Prints `first = 3` then panics on `push`
> `first` borrows `scores` immutably, but its last use is the first `println!`. By the time `push` needs a mutable borrow, the shared one has ended, so it compiles. Move the `println!("first = {first}")` *after* the `push` and you get E0502: the push might reallocate the vector, which would leave `first` pointing at freed memory. The compiler tracks this precisely.

--- card: read id=c16 xp=5 title="Slices: a view into a sequence"
A **slice** is a reference to a contiguous part of a collection: a pointer plus a length. It does not own anything.

```rust
let s = String::from("hello world");
let hello = &s[0..5];   // "hello"
let world = &s[6..];    // "world"   (.. to the end)
let all   = &s[..];     // the whole thing
```

The type of a string slice is `&str`. Two facts fall out of this:

- A **string literal** `"hello"` is a `&str`: a slice pointing into the program's read-only data.
- A `&String` can be turned into a `&str` for free (deref coercion), so a function that takes `&str` accepts literals, `&String`s and sub-slices alike. **Prefer `&str` parameters over `&String`.**

Slices are borrows, so the borrowing rules apply. If a function returns `&str` into its input, the compiler will not let you clear the input while the slice is alive. That is precisely the bug class slices prevent.

Indices are **byte** offsets, and slicing in the middle of a multi-byte UTF-8 character panics. Chapter 8 returns to that.

--- card: predict id=c17 xp=15 title="Slice arithmetic"
```rust
fn main() {
    let s = String::from("missile launcher");
    let a = &s[..7];
    let b = &s[8..];
    println!("[{a}] [{b}] {}", a.len() + b.len());
}
```
? What is printed?
- [x] `[missile] [launcher] 15`
- [ ] `[missile] [launcher] 16`
- [ ] `[missile ] [launcher] 16`
- [ ] Compile error: cannot have two slices of `s`
> `..7` is bytes 0 to 6, `8..` skips the space at index 7. Two shared borrows at once are fine. The lengths add up to 15 because the space is in neither slice.

--- card: read id=c19 xp=5 title="Slices of anything"
Slices are not only for strings. `&[i32]` is a slice of integers, and a `&Vec<i32>` or a `&[i32; 3]` array reference coerces to one.

```rust
fn sum(values: &[i32]) -> i32 {
    values.iter().sum()
}

let v = vec![1, 2, 3];
let a = [4, 5, 6];
sum(&v);        // whole vector
sum(&v[1..]);   // part of it
sum(&a);        // array too
```

The same guidance as for strings: a function that reads a sequence should take `&[T]`, not `&Vec<T>`.

**Chapter summary.** Values have one owner. Assignment and function calls move non-`Copy` values. References borrow without owning: many readers *or* one writer, never dangling. Slices are borrowed views into sequences. Every other chapter builds on these ideas.
