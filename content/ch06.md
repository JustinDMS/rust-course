# Chapter 6: Enums and Pattern Matching

--- card: read id=c01 xp=5 title="An enum is one of several things"
A struct says *and*: a rectangle has a width **and** a height. An **enum** says *or*: an IP address is V4 **or** V6.

```rust
enum IpAddrKind {
    V4,
    V6,
}

let four = IpAddrKind::V4;
```

Each **variant** can carry data, and different variants can carry different data:

```rust
enum Message {
    Quit,                       // no data
    Move { x: i32, y: i32 },    // named fields, like a struct
    Write(String),              // one value, like a tuple struct
    ChangeColor(i32, i32, i32), // three values
}
```

A `Message` value is exactly one of those four, and the compiler knows the full list. Enums can have `impl` blocks and methods just like structs. If you come from C, note that Rust enums are *tagged unions*: the variant tag and its payload travel together, and you can never read the wrong one.

*Book: 6.1 "Defining an Enum"*

--- card: read id=c02 xp=5 title="Option: the enum that replaces null"
Rust has no `null`. Instead, a value that might be absent has the type `Option<T>`:

```rust
enum Option<T> {
    None,
    Some(T),
}
```

`Some` and `None` are in scope everywhere without a prefix. The payoff: an `Option<i32>` is **not** an `i32`, so `Some(5) + 1` does not compile. You cannot forget to handle the empty case, because the compiler will not let you use the value until you have taken it out of the `Option`. That removes the billion-dollar mistake at the type level.

Taking it out means `match`, `if let`, or one of the many helper methods: `unwrap_or(default)`, `map`, `is_some`, `unwrap` (which panics on `None`; fine in tests and prototypes, a smell in library code), and `expect("why this cannot be None")`.

--- card: predict id=c03 xp=15 title="Adding to an Option"
```rust
fn main() {
    let x: i8 = 5;
    let y: Option<i8> = Some(5);
    let sum = x + y;
    println!("{sum}");
}
```
? What happens?
- [ ] Prints `10`
- [x] Compile error: cannot add `Option<i8>` to `i8`
- [ ] Prints `Some(10)`
- [ ] Panics at run time because `y` might be `None`
> `i8` and `Option<i8>` are different types, and there is no `+` between them. You first have to say what should happen when `y` is `None`: `x + y.unwrap_or(0)`, or a `match`.

--- card: read id=c04 xp=5 title="match"
`match` compares a value against **patterns** and runs the code of the first one that fits. Patterns can destructure variants and bind their data:

```rust
enum Coin { Penny, Nickel, Dime, Quarter(UsState) }

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny => 1,
        Coin::Nickel => 5,
        Coin::Dime => 10,
        Coin::Quarter(state) => {
            println!("State quarter from {state:?}!");
            25
        }
    }
}
```

Two rules make `match` what it is:

1. **Exhaustive.** Every possible value must be covered, or it is a compile error. Add a variant later and every `match` that forgets it stops compiling. That is the feature.
2. **An expression.** Each arm produces a value; all arms must agree on the type.

The catch-all patterns: a name (`other => ...`) binds the value; `_` ignores it. Put them last, because arms are tried in order.

```rust
fn plus_one(x: Option<i32>) -> Option<i32> {
    match x {
        None => None,
        Some(i) => Some(i + 1),
    }
}
```

--- card: predict id=c05 xp=15 title="Missing arm"
```rust
enum Dir { North, South, East, West }

fn turn_back(d: Dir) -> Dir {
    match d {
        Dir::North => Dir::South,
        Dir::South => Dir::North,
        Dir::East => Dir::West,
    }
}

fn main() {
    let _ = turn_back(Dir::West);
}
```
? What happens?
- [ ] Returns `Dir::West` unchanged
- [ ] Panics at run time: no arm matched
- [x] Compile error: non-exhaustive patterns: `Dir::West` not covered
- [ ] Compile error: `match` arms have incompatible types
> The compiler lists exactly which variants are missing. There is no run-time "no arm matched" in Rust; it cannot happen, because the check is done before the program exists.

--- card: quiz id=c06 xp=15 title="Match arms" multi
```rust
fn describe(n: Option<u32>) -> &'static str {
    match n {
        Some(0) => "zero",
        Some(x) if x > 100 => "big",
        Some(_) => "some",
        None => "nothing",
    }
}
```
? Which calls return `"some"`?
- [ ] `describe(Some(0))`
- [x] `describe(Some(7))`
- [x] `describe(Some(100))`
- [ ] `describe(Some(101))`
- [ ] `describe(None)`
> Arms are tried top to bottom. `Some(0)` is caught first; `if x > 100` is a *match guard* that only lets values over 100 through; `Some(_)` takes every other `Some`. `100` is not `> 100`, so it is `"some"`.

--- card: read id=c07 xp=5 title="if let and let else"
When you care about **one** pattern and want to ignore the rest, a full `match` is noisy:

```rust
match config_max {
    Some(max) => println!("max is {max}"),
    _ => (),
}
```

`if let` says the same thing in one line, and may have an `else`:

```rust
if let Some(max) = config_max {
    println!("max is {max}");
} else {
    println!("no max");
}
```

You trade exhaustiveness for brevity: the compiler no longer checks that you thought about every variant. Use it when that is what you want.

**`let else`** is for the "happy path continues, otherwise bail out" shape:

```rust
fn describe(coin: Coin) -> String {
    let Coin::Quarter(state) = coin else {
        return String::from("not a quarter");
    };
    format!("a quarter from {state:?}")   // `state` is in scope here
}
```

The `else` block must *diverge*: `return`, `continue`, `break` or `panic!`. After it, the bindings from the pattern are available in the rest of the function, without nesting.

*Book: 6.3 "Concise Control Flow with if let and let else"*

--- card: predict id=c08 xp=15 title="Early exit"
```rust
fn first_even(values: &[i32]) -> String {
    let Some(&first) = values.first() else {
        return String::from("empty");
    };
    if first % 2 == 0 {
        format!("{first} is even")
    } else {
        format!("{first} is odd")
    }
}

fn main() {
    println!("{}", first_even(&[]));
    println!("{}", first_even(&[7, 2]));
}
```
? What is printed?
- [x] `empty` then `7 is odd`
- [ ] `empty` then `2 is even`
- [ ] Compile error: `else` on a `let` is not allowed
- [ ] Panics on the empty slice
> `values.first()` is `None` for an empty slice, so the `else` runs and returns early. For `[7, 2]` it is `Some(&7)`; the pattern `Some(&first)` binds `first = 7`, which is odd. The function looks only at the first element.

? Which statements are true?
- [x] A `match` that does not cover every variant is a compile error.
- [ ] `Option<T>` is a special compiler feature rather than an ordinary enum.
- [x] `if let` checks one pattern and does not require handling the others.
- [x] The `else` block of a `let else` must return, break, continue or panic.
- [ ] `unwrap()` on `None` returns a default value.
- [x] Enum variants can hold different kinds of data from one another.
> `Option` is defined in the standard library as a plain two-variant enum; its only special treatment is being imported everywhere. `unwrap()` on `None` panics, which is why `unwrap_or`, `match` and `let else` exist.
