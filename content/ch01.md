# Chapter 1: Getting Started

--- card: read id=c01 xp=5 title="What is already on this machine"
Rust is installed through **rustup**, which manages toolchains (stable, beta, nightly) and keeps them updated.

```text
rustc --version      # the compiler
cargo --version      # the build tool and package manager
rustup update        # pull the newest stable release
rustup doc           # open the offline docs in a browser
```

This course was built against stable Rust 1.95 with the 2024 edition. Everything in it works on any stable release from 1.85 onwards.

You will almost never call `rustc` directly. **Cargo** drives the compiler, resolves dependencies, runs tests and formats code. This whole course runs through it: the web app you are reading right now is `cargo run -p course`.

--- card: read id=c02 xp=5 title="Anatomy of Hello, World"
```rust
fn main() {
    println!("Hello, world!");
}
```

Four things to notice:

- `fn main()` is the entry point. Every binary has exactly one.
- Function bodies live in `{ }`. Rust style puts the opening brace on the same line and indents with four spaces. `cargo fmt` does this for you; never argue with it.
- `println!` ends in `!`, which means it is a **macro**, not a function. Macros generate code at compile time; `println!` checks your format string against its arguments before the program ever runs.
- The line ends with `;`. Most lines do. The exceptions matter and show up in chapter 3.

*Book: 1.2 "Hello, World!"*

--- card: code id=c03 xp=5 title="Run it"
```rust
fn main() {
    println!("Hello, world!");
    let name = "Rustacean";
    println!("Hello, {name}!");       // inline variable in the format string
    println!("{} + {} = {}", 2, 3, 2 + 3);   // positional arguments
}
```
Format strings can name variables directly (`{name}`) or take arguments in order (`{}`). Both are checked at compile time: remove an argument and the program will not build.

--- card: quiz id=c04 xp=10 title="The exclamation mark"
? What does the `!` in `println!` tell you?
- [ ] The call can fail and will panic on error
- [x] `println!` is a macro, expanded at compile time
- [ ] The output is flushed immediately
- [ ] The function takes a variable number of arguments, like C's `printf`
> The `!` marks a macro invocation. Macros can do things functions cannot, such as accept a variable number of arguments and inspect the format string at compile time. `vec![]`, `format!`, `assert_eq!` and `todo!` are the others you will meet soon.

--- card: read id=c05 xp=5 title="Cargo in one screen"
```text
cargo new hello        # new project: Cargo.toml + src/main.rs + git repo
cargo build            # compile to target/debug/
cargo run              # build if needed, then run
cargo check            # type-check only; much faster, no binary
cargo build --release  # optimised build in target/release/
cargo test             # build and run the tests
cargo fmt              # format every file
cargo clippy           # extra lints (install with rustup component add clippy)
```

`Cargo.toml` describes the package: its name, edition and dependencies. `Cargo.lock` records the exact dependency versions that were resolved, so a build is reproducible. Commit both.

In a **workspace** (like this course) one root `Cargo.toml` lists several packages, and `-p <name>` picks one: `cargo test -p ch04_ownership`.

*Book: 1.3 "Hello, Cargo!"*

--- card: quiz id=c06 xp=10 title="Fast feedback" fill
? Which cargo subcommand checks that your code compiles **without** producing an executable? (just the subcommand)
= check | cargo check
> `cargo check` runs the front half of the compiler and skips code generation. Use it constantly while writing; `cargo build` or `cargo run` when you want to execute something.

--- card: read id=c07 xp=5 title="How the exercises in this course work"
Every chapter has a crate under `exercises/`, and every exercise is one file in it, compiled on its own as a test target:

```text
exercises/ch01_getting_started/ex01_hello.rs
cargo test -p ch01_getting_started --test ex01_hello
```

Each file starts with a doc comment (`//!`) that says what to do, then the code, then `#[test]` functions that decide whether you are done. **Do not edit the tests.** The *Run tests* button in an exercise card runs exactly that cargo command and shows you the compiler's output.

A function body of `todo!()` compiles but panics when called: it is a placeholder you replace. A file that does not compile yet is a *fix* exercise: read the errors from the top, the first one is usually the real one.

Hints are free. The solution unlocks after two attempts and halves the XP, so try the hints first.

--- card: quiz id=c08 xp=10 title="Lock file" 
? What is `Cargo.lock` for?
- [ ] It locks the project so two builds cannot run at once
- [x] It pins the exact versions of every dependency that were resolved, for reproducible builds
- [ ] It caches compiled dependencies between builds
- [ ] It lists which files are part of the package
> `Cargo.toml` says what you *want* (`rand = "0.9"`); `Cargo.lock` records what you *got* (`rand 0.9.2` plus every transitive dependency). Compiled artefacts live in `target/`, which is not committed.
