# Chapter 3: Common Programming Concepts

--- card: read id=c01 xp=5 title="Variables are immutable by default"
```rust
let x = 5;
x = 6;        // error[E0384]: cannot assign twice to immutable variable
```

A plain `let` binding cannot be changed. Add `mut` when you intend to change it:

```rust
let mut x = 5;
x = 6;        // fine
```

This is not Rust being difficult. When you read code and see a binding without `mut`, you know its value never changes, and the compiler knows it too. Most bindings turn out not to need `mut`, and when one does, the keyword documents the intent.

**Constants** are different again: `const MAX_POINTS: u32 = 100_000;`. Always immutable, the type is required, the value must be computable at compile time, and the name is SCREAMING_SNAKE_CASE. They can live at module level, outside any function.

*Book: 3.1 "Variables and Mutability"*

--- card: read id=c03 xp=5 title="Shadowing"
You can declare a new variable with the same name as an old one. The new one **shadows** the old one from that point on.

```rust
let spaces = "   ";          // a &str
let spaces = spaces.len();   // now a usize; the old binding is gone
```

Shadowing is not mutation. Each `let` creates a fresh, immutable binding, and the type may change. With `mut` you could not do that:

```rust
let mut spaces = "   ";
spaces = spaces.len();       // error: expected &str, found usize
```

Use shadowing when a value goes through transformations and keeping the same name reads better than `input_str`, `input_trimmed`, `input_num`.

--- card: predict id=c04 xp=15 title="Inner scope"
```rust
fn main() {
    let x = 5;
    let x = x + 1;
    {
        let x = x * 2;
        println!("inner x = {x}");
    }
    println!("outer x = {x}");
}
```
? What is printed?
- [x] `inner x = 12` then `outer x = 6`
- [ ] `inner x = 12` then `outer x = 12`
- [ ] `inner x = 10` then `outer x = 5`
- [ ] Compile error: `x` is declared three times
> The second `let x` shadows the first with 6. Inside the block a third `x` is 12, but it ends with the block, so the outer `println!` sees 6 again.

--- card: read id=c05 xp=5 title="Scalar types"
Rust is statically typed and usually infers the type, but every value has exactly one.

| Kind | Types | Notes |
| --- | --- | --- |
| Integers | `i8 i16 i32 i64 i128 isize`, `u8 ... usize` | `i32` is the default; `usize` indexes collections |
| Floats | `f32`, `f64` | `f64` is the default |
| Boolean | `bool` | `true` / `false`, one byte |
| Character | `char` | a Unicode scalar value, 4 bytes, written `'z'` |

Integer literals can carry a suffix (`57u8`), underscores (`1_000_000`), and prefixes (`0xff`, `0o77`, `0b1111_0000`, `b'A'` for a byte).

**Overflow**: in a debug build, `255u8 + 1` panics. In a release build it wraps to 0. When wrapping, saturating or detecting overflow is what you *mean*, say so with `wrapping_add`, `saturating_add`, `checked_add` (returns an `Option`) or `overflowing_add`.

Integer division truncates toward zero: `-7 / 2` is `-3`. There is no implicit conversion between numeric types: `let f: f64 = 3;` is an error, and so is `i32 + i64`. Convert with `as` (`x as f64`) or `From`/`try_into` (later).

*Book: 3.2 "Data Types"*

--- card: predict id=c06 xp=15 title="Two hundred and fifty-six"
```rust
fn main() {
    let x: u8 = 255;
    let y = x + 1;
    println!("{y}");
}
```
? What happens in a debug build (`cargo run`, `cargo test`)?
- [ ] Prints `256`
- [ ] Prints `0`
- [x] Compile error: this arithmetic operation will overflow
- [ ] Panics at run time: attempt to add with overflow
> The compiler can see the whole computation here, so it refuses with a deny-by-default lint. If `x` came from input instead, the same code would compile and **panic** at run time in debug builds (and wrap to 0 in release). Use `x.wrapping_add(1)` or `x.checked_add(1)` when you mean it.

--- card: read id=c07 xp=5 title="Tuples and arrays"
A **tuple** groups values of different types. Its length is fixed.

```rust
let tup: (i32, f64, u8) = (500, 6.4, 1);
let (x, y, z) = tup;      // destructuring
let first = tup.0;        // index by position
```

The empty tuple `()` is called **unit**. A function with no return type returns it.

An **array** holds values of one type, and its length is part of the type.

```rust
let a = [1, 2, 3, 4, 5];       // [i32; 5]
let zeros = [0u8; 32];          // 32 copies of 0
let third = a[2];
```

Arrays live on the stack. Indexing past the end **panics** at run time (or fails to compile when the index is a constant), rather than reading whatever memory happens to be there. When you want a list that grows, that is `Vec`, chapter 8.

--- card: predict id=c08 xp=15 title="Off the end"
```rust
fn main() {
    let days = ["mon", "tue", "wed"];
    let index = days.len();
    println!("{}", days[index]);
}
```
? What happens?
- [ ] Prints an empty string
- [ ] Prints `wed`
- [x] Panics: index out of bounds: the len is 3 but the index is 3
- [ ] Compile error: cannot index with a `usize`
> Valid indices are 0, 1 and 2. Rust checks every array index at run time and panics on an invalid one instead of reading garbage. (Write `days[3]` with a literal and the compiler catches it before you even run.)

--- card: read id=c09 xp=5 title="Functions, statements and expressions"
```rust
fn plus_one(x: i32) -> i32 {
    x + 1
}
```

Parameter types are mandatory. The return type comes after `->`. And the body's **last expression, without a semicolon, is the return value**.

Rust distinguishes:

- **Statements** do something and produce no value: `let y = 6;`, a function definition, any expression followed by `;`.
- **Expressions** produce a value: `5 + 6`, a function call, a block `{ ... }`, `if`, `match`, `loop`.

So this does *not* compile: `let x = (let y = 6);`, because `let` is a statement. And this returns `()` instead of a number, because the semicolon turned the expression into a statement:

```rust
fn plus_one(x: i32) -> i32 {
    x + 1;     // error[E0308]: mismatched types, expected i32, found ()
}
```

The compiler even suggests removing the semicolon. `return x + 1;` works too and is used for early exits.

--- card: read id=c12 xp=5 title="if is an expression"
```rust
let number = 6;
if number % 4 == 0 {
    println!("divisible by 4");
} else if number % 3 == 0 {
    println!("divisible by 3");
} else {
    println!("neither");
}
```

The condition **must** be a `bool`. `if number { ... }` with an integer is a compile error; write `if number != 0`.

Because `if` is an expression, it can produce a value:

```rust
let size = if hp > 50 { "big" } else { "small" };
```

Both branches must have the **same type**. `if cond { 5 } else { "six" }` is rejected, because `size` would have no single type.

--- card: read id=c13 xp=5 title="Three loops"
**`loop`** repeats until `break`, and `break` can carry a value:

```rust
let mut counter = 0;
let result = loop {
    counter += 1;
    if counter == 10 {
        break counter * 2;     // result = 20
    }
};
```

Nested loops can **label** which one to break: `'outer: loop { ... break 'outer; }`.

**`while`** repeats while a condition holds:

```rust
while number != 0 {
    number -= 1;
}
```

**`for`** walks anything iterable, and is the loop you will write most. Ranges are iterable:

```rust
for element in [10, 20, 30] { println!("{element}"); }
for i in 1..4 { }           // 1, 2, 3
for i in (1..=3).rev() { }  // 3, 2, 1
```

`for` over a collection cannot go out of bounds and has no index to get wrong. Reach for `while` with an index only when the index itself matters.

--- card: predict id=c14 xp=15 title="Which loop ends?"
```rust
fn main() {
    let mut count = 0;
    'outer: loop {
        let mut inner = 0;
        loop {
            inner += 1;
            count += 1;
            if inner == 3 { break; }
            if count == 7 { break 'outer; }
        }
    }
    println!("{count}");
}
```
? What is printed?
- [ ] `3`
- [x] `7`
- [ ] `9`
- [ ] The program never ends
> The plain `break` leaves only the inner loop, after 3 iterations each time. On the seventh increment overall, `break 'outer` leaves both loops. Labels let you say which loop you mean.
