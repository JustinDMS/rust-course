# Chapter 7: Managing Growing Projects with Packages, Crates, and Modules

--- card: read id=c01 xp=5 title="Packages and crates"
A **crate** is the unit of compilation: one tree of modules that becomes one library or one executable.

- A **binary crate** has a `main` function and produces an executable. `src/main.rs` is its root.
- A **library crate** has no `main`; other crates use it. `src/lib.rs` is its root.

A **package** is what `cargo new` makes: a `Cargo.toml` plus one or more crates. It may hold at most one library crate and any number of binaries. The guessing game in chapter 2 is a package with both: `main.rs` calls into `lib.rs`, and the tests call into `lib.rs` too.

This course is a **workspace**: one root `Cargo.toml` that lists many packages (`course`, each `exercises/chNN_*`, each project) and shares one `target/` directory and one `Cargo.lock` between them.

*Book: 7.1 "Packages and Crates"*

--- card: read id=c02 xp=5 title="Modules and the module tree"
Inside a crate, **modules** group code and control what is visible. `mod` declares one:

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
        fn seat_at_table() {}
    }

    mod serving {
        fn take_order() {}
    }
}
```

That forms a tree rooted at the crate:

```text
crate
└── front_of_house
    ├── hosting
    │   ├── add_to_waitlist
    │   └── seat_at_table
    └── serving
        └── take_order
```

A module's body can be written inline in braces, as above, or live in its own file (later in this chapter). Either way the tree is the same, and **paths** walk it.

*Book: 7.2 "Defining Modules to Control Scope and Privacy"*

--- card: read id=c03 xp=5 title="Paths and privacy"
A path is like a filesystem path with `::` as the separator.

- **Absolute**: starts at the crate root. `crate::front_of_house::hosting::add_to_waitlist()`.
- **Relative**: starts in the current module. `front_of_house::hosting::add_to_waitlist()` from the root, or `super::serve()` to reach the parent module (like `..`).

The privacy rules:

1. Everything is **private by default**: functions, structs, enums, modules, constants.
2. A child module can see everything in its ancestors, private or not. An ancestor cannot see a child's private items.
3. `pub` makes an item visible to the parent, and to anyone who can reach the parent. A `pub` function inside a private module is still unreachable from outside that module's parent.
4. `pub struct` makes the struct public but **its fields stay private** unless each is marked `pub`. A struct with private fields can only be created through a constructor function it provides.
5. `pub enum` makes **all its variants** public. There is no point in a public enum with hidden variants.

*Book: 7.3 "Paths for Referring to an Item in the Module Tree"*

--- card: predict id=c04 xp=15 title="Who can call what?"
```rust
mod garage {
    pub mod tools {
        pub fn wrench() -> &'static str { "wrench" }
        fn secret() -> &'static str { "secret" }
    }
    fn inventory() -> &'static str { tools::wrench() }
}

fn main() {
    println!("{}", garage::tools::wrench());
    println!("{}", garage::inventory());
}
```
? What happens?
- [ ] Prints `wrench` then `wrench`
- [x] Compile error: function `inventory` is private
- [ ] Compile error: function `secret` is never used
- [ ] Compile error: module `tools` must be declared at the crate root
> `inventory` has no `pub`, so `main` (in the crate root, the parent of `garage`) cannot call it. `inventory` itself calling `tools::wrench()` is fine: `tools` is `pub` and `wrench` is `pub`. The unused `secret` is only a warning.

--- card: read id=c06 xp=5 title="use: bringing paths into scope"
Writing the full path every time is tedious. `use` creates a shortcut that is valid for the rest of the module it appears in:

```rust
use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist();
}
```

Idioms worth copying:

- For **functions**, import the *parent module* and call `hosting::add_to_waitlist()`. It stays clear that the function is not defined locally.
- For **structs, enums and traits**, import the *type itself*: `use std::collections::HashMap;`.
- When two imports clash, rename with `as`: `use std::io::Result as IoResult;`.
- Nested paths shorten related imports: `use std::{cmp::Ordering, io};` and `use std::io::{self, Write};`.
- The glob `use std::collections::*;` pulls in everything. Mostly seen in tests and preludes; avoid it elsewhere, because it hides where names come from.

A `use` is private to its module too. **`pub use`** re-exports: it makes the imported name part of your module's public API, so users of your crate can write `restaurant::hosting::add_to_waitlist` even though `hosting` lives deeper in the tree. Libraries use this to offer a flat, convenient surface over a deep internal structure.

*Book: 7.4 "Bringing Paths into Scope with the use Keyword"*

--- card: predict id=c07 xp=15 title="Scope of a use"
```rust
mod shapes {
    pub fn circle() -> &'static str { "circle" }
}

use shapes::circle;

mod drawing {
    pub fn draw() -> &'static str { circle() }
}

fn main() {
    println!("{}", drawing::draw());
}
```
? What happens?
- [ ] Prints `circle`
- [x] Compile error: cannot find function `circle` in this scope (inside `drawing`)
- [ ] Compile error: `use` must come before any `mod`
- [ ] Prints an empty line
> The `use` lives in the crate root, and `drawing` is a different module with its own scope. Inside `drawing` you need `super::circle()`, `super::shapes::circle()`, or its own `use super::shapes::circle;`.

--- card: read id=c08 xp=5 title="Modules in separate files"
Inline modules are fine for small things. For anything larger, put the body in a file and leave only the declaration:

```rust
// src/lib.rs
pub mod inventory;      // body is in src/inventory.rs
```

```rust
// src/inventory.rs
pub mod items;          // body is in src/inventory/items.rs
pub fn total() -> u32 { items::count() }
```

```rust
// src/inventory/items.rs
pub fn count() -> u32 { 3 }
```

The rules:

- `mod name;` (with a semicolon) tells the compiler to load `name.rs` next to the current file, or `name/mod.rs` (the older style; it works, but mixing the two styles in one project is confusing).
- Submodules of a file module go in a directory with the same name: `inventory.rs` plus `inventory/items.rs`.
- A file that is not reached by some `mod` declaration is **not part of the crate**. It is not compiled at all, and nothing in it exists. Forgetting the `mod` line is a classic.
- Moving a module into a file does not change any path. `crate::inventory::items::count` is the same either way.

*Book: 7.5 "Separating Modules into Different Files"*
