# Chapter 9: Error Handling

--- card: read id=c01 xp=5 title="Two kinds of errors"
Rust splits errors into two groups and gives each its own tool.

**Unrecoverable** errors are bugs: an index past the end of an array, an invariant that cannot hold. The program cannot sensibly continue. The tool is `panic!`, which prints a message, unwinds the stack (running destructors), and exits the thread. You call it yourself with `panic!("...")`, or something calls it for you: out-of-range indexing, `unwrap()` on `None`, integer overflow in debug builds.

```text
thread 'main' panicked at src/main.rs:4:6:
index out of bounds: the len is 3 but the index is 99
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**Recoverable** errors are expected situations: a file is missing, the input is not a number, the network is down. The caller should be able to react. The tool is the `Result` type, and the rest of this chapter is about using it well.

There are no exceptions. A function that can fail says so in its return type, and the compiler makes sure every caller notices.

*Book: 9.1 "Unrecoverable Errors with panic!"*

--- card: read id=c02 xp=5 title="Result"
```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`T` is the success value, `E` the error value. Like `Option`, it is an ordinary enum with its variants imported everywhere. Everything that can fail returns one: `File::open`, `"42".parse()`, `read_line`.

```rust
use std::fs::File;

let greeting_file = match File::open("hello.txt") {
    Ok(file) => file,
    Err(error) => panic!("Problem opening the file: {error:?}"),
};
```

Shortcuts for when you do want to panic on `Err`:

- `.unwrap()` panics with the error's debug output.
- `.expect("the config file should exist next to the binary")` panics with your message, which is far more useful in a stack trace. Prefer it over `unwrap` outside tests and quick experiments.

Shortcuts for when you want a fallback: `.unwrap_or(default)`, `.unwrap_or_else(|e| ...)`, `.unwrap_or_default()`, `.ok()` to turn a `Result` into an `Option`, and `.map_err(f)` to change the error type.

*Book: 9.2 "Recoverable Errors with Result"*

```rust
fn main() {
    let a = "12".parse::<i32>();
    let b = "twelve".parse::<i32>();
    println!("{}", a.unwrap_or(0));
    println!("{}", b.unwrap_or(0));
    println!("{}", "x".parse::<i32>().expect("x should be a number"));
}
```
? What happens?
- [ ] Prints `12`, `0`, then `0`
- [x] Prints `12`, `0`, then panics with `x should be a number: ParseIntError { kind: InvalidDigit }`
- [ ] Panics at the second `println!`
- [ ] Compile error: `unwrap_or` cannot be used on a `Result`
> `unwrap_or` swaps an `Err` for the fallback and never panics. `expect` panics on an `Err`, printing your message followed by the error's debug form. Note that `unwrap_or` and `expect` take `self`: a `Result` whose error type is not `Copy` is moved by the call, so you cannot call them twice on the same value.

--- card: read id=c04 xp=5 title="Propagating errors with ?"
Most functions do not know what to do about an error; they hand it to the caller. Written out:

```rust
fn read_username(path: &str) -> Result<String, io::Error> {
    let mut file = match File::open(path) {
        Ok(f) => f,
        Err(e) => return Err(e),
    };
    let mut username = String::new();
    match file.read_to_string(&mut username) {
        Ok(_) => Ok(username),
        Err(e) => Err(e),
    }
}
```

The **`?` operator** is exactly that `match`:

```rust
fn read_username(path: &str) -> Result<String, io::Error> {
    let mut username = String::new();
    File::open(path)?.read_to_string(&mut username)?;
    Ok(username)
}
```

`expr?` on a `Result`: if it is `Ok(v)`, the expression evaluates to `v`; if it is `Err(e)`, the function **returns** `Err(e.into())` immediately. That `.into()` matters: the error is converted with the `From` trait into the function's declared error type, so one function can collect several kinds of failure into one error type with a few `From` impls.

`?` also works on `Option` inside a function that returns `Option`: `None` returns early.

The rule: `?` can only be used in a function whose return type matches (`Result` in a function returning `Result`, `Option` in one returning `Option`). In `main`, that means declaring `fn main() -> Result<(), Box<dyn Error>>`.

*Book: 9.2 "A Shortcut for Propagating Errors: the ? Operator"*

--- card: predict id=c05 xp=15 title="Question mark in main"
```rust

fn main() {
    let f = File::open("hello.txt")?;
    println!("{f:?}");

```
? What happens?
- [ ] Compiles; panics at run time if the file is missing
- [x] Compile error: the `?` operator can only be used in a function that returns `Result` or `Option`
- [ ] Compiles; prints nothing if the file is missing
- [ ] Compile error: `File` does not implement `Debug`
> `?` needs somewhere to return the error to. `main` returning `()` has nowhere. Change it to `fn main() -> Result<(), Box<dyn std::error::Error>>` and add `Ok(())` at the end, and a failed open becomes a non-zero exit code with the error printed.

--- card: quiz id=c06 xp=15 title="Where ? is allowed" multi
? In which functions can `line.parse::<i32>()?` appear?
- [x] `fn a() -> Result<i32, std::num::ParseIntError>`
- [x] `fn b() -> Result<i32, Box<dyn std::error::Error>>`
- [ ] `fn c() -> i32`
- [ ] `fn d() -> Option<i32>`
- [ ] `fn e() -> Result<(), String>`
> The error must convert into the function's error type via `From`. `ParseIntError` converts to itself and to `Box<dyn Error>` (any `Error` type does). There is no `From<ParseIntError> for String`, so `e` needs `.map_err(|e| e.to_string())?` instead. A `Result` does not convert to an `Option` (use `.ok()?` for that), and a function returning plain `i32` has no error channel at all.

--- card: read id=c07 xp=5 title="Box<dyn Error> and custom errors"
When a function can fail in several ways and the caller only needs to print the error, the type `Box<dyn std::error::Error>` means "some error, on the heap". Every standard error converts into it, so `?` just works:

```rust
fn load(path: &str) -> Result<Config, Box<dyn Error>> {
    let text = std::fs::read_to_string(path)?;        // io::Error
    let port: u16 = text.trim().parse()?;             // ParseIntError
    Ok(Config { port })
}
```

When callers need to **tell errors apart**, define an enum:

```rust
#[derive(Debug)]
enum ConfigError {
    Missing(String),
    BadNumber(std::num::ParseIntError),
}

impl std::fmt::Display for ConfigError { /* human text */ }
impl std::error::Error for ConfigError {}

impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self { ConfigError::BadNumber(e) }
}
```

With that `From` impl, `text.parse()?` inside a function returning `Result<_, ConfigError>` wraps the parse error automatically. The `Display` and `Error` impls let a `ConfigError` be printed, and be boxed into a `Box<dyn Error>` further up. (The `impl` syntax is chapter 10; here, copy the shape.)

--- card: read id=c08 xp=5 title="To panic or not to panic"
`Result` is the default for anything that can fail for reasons outside your code. Reach for `panic!` (or `unwrap`/`expect`) when:

- **You are in a test, example or prototype.** A panic is the right way to fail a test.
- **You know more than the compiler.** `"127.0.0.1".parse::<IpAddr>().expect("hardcoded IP is valid")`: the literal cannot fail to parse, and `expect` documents why.
- **A contract was violated.** If a function's doc says "index must be in range" and it is not, the *caller* has a bug. Panicking there is better than carrying on with corrupt state.

And use the **type system** to make invalid states unrepresentable, so there is nothing to check:

```rust
pub struct Guess { value: i32 }

impl Guess {
    pub fn new(value: i32) -> Guess {
        if !(1..=100).contains(&value) {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }
        Guess { value }
    }
    pub fn value(&self) -> i32 { self.value }
}
```

With `value` private, a `Guess` can only exist through `new`, so every function that takes a `Guess` knows it is in range. Validation happens once, at the boundary.

*Book: 9.3 "To panic! or Not to panic!"*
